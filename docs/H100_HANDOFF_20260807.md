## 1. 怎么连

**两跳结构**:本地 →(ssh 别名 `aws-hpc`)→ 头节点 →(私网)→ p5 计算盒。

```bash
# 1) 头节点(有 AWS CLI 与 /shared;注意它是 t3.medium,只有 3GB 内存,不要在上面编译大工程)
ssh aws-hpc

# 2) p5 计算盒(必须从本地跳,头节点上没有这把 pem)
ssh -J aws-hpc -i ~/.ssh/aws-hpc-us.pem -o StrictHostKeyChecking=no ec2-user@<P5_PRIVATE_IP>
```

**本机 IP 从哪来**:自动起机脚本会把它写进 `/shared/npr10_ab/newbox.env`:
```

```
或直接查:
```bash
ssh aws-hpc 'aws ec2 describe-instances --region us-east-2 \
  --filters "Name=instance-state-name,Values=running" "Name=instance-type,Values=p5.48xlarge" \
  --query "Reservations[].Instances[].[InstanceId,PrivateIpAddress,CapacityReservationId]" --output text'
```

## 4. 编译(四个已知坑,全部踩过)

算例 `GNUmakefile` 模板:
```make
DEBUG   = FALSE
DIM     = 2                      # 或 3
COMP    = gnu
CXXSTD  = c++20                  # ← 坑 4.2
PRECISION = DOUBLE
TINY_PROFILE = TRUE
USE_MPI  = TRUE
USE_CUDA = TRUE
CUDA_ARCH = 90                   # H100 = sm_90
USE_OMP  = FALSE
USE_GPIBM = FALSE
AMREX_NO_PROBINIT = TRUE
AMR_SOLVER = /shared/<求解器树>
AMREX_HOME = $(AMR_SOLVER)/lib/amrex
CEXE_headers += prob.h
include $(AMR_SOLVER)/src/Make.CNS
```
编译命令(**在 p5 上编,不要在头节点**,那里只有 3GB 内存):
```bash
cd <case_dir>
rm -rf tmp_build_dir *CUDA.ex        # ← 坑 4.4
make -j24 USE_MPI=TRUE USE_CUDA=TRUE CUDA_ARCH=90 DIM=2 > build.log 2>&1
ls *CUDA.ex && cuobjdump *CUDA.ex | grep -o 'sm_[0-9]*' | sort -u   # 应为 sm_90
```

### 4.1 坑:CUDA 13 编不过 AMReX
```
error: namespace "cuda" has no member "minimum" / "maximum"
       in Src/Base/AMReX_GpuReduce.H
```
原因:CUDA 13 的 CCCL≥3 把 cub 归约算子搬进了 `cuda::` 命名空间。
**解法**:①用 CUDA 12.6(见第 3 节);②amrex 必须是**带 CCCL guard 的版本**——
用 `/shared/cerisse_h100_latest/lib/amrex` 或 `/shared/cerisse_local_20260805/lib/amrex`
(校验:`grep -c AMREX_CUDA_CCCL_VER_GE_3 <amrex>/Src/Base/AMReX_GpuReduce.H` 应 ≥1)。
**`/shared/cerisse_reflux/lib/amrex` 没有 guard,会失败。**

### 4.2 坑:`CXXSTD=c++17` 编不过
求解器用了 C++20 的 `requires` 表达式:
```
error: 'requires' was not declared in this scope   (src/rhs/viscous.h 等)
```
**必须 `CXXSTD = c++20`。**

### 4.3 坑(最隐蔽):nvcc 的 constexpr-if 捕获限制
```
error: An extended __device__ lambda cannot first-capture variable
       in constexpr-if context
```
**CPU 编译不会报,只有 nvcc 报**——所以本地改完代码上 GPU 才炸。
原因:某变量在 device lambda **外**声明,却**首次**在 `if constexpr (...)` 分支里使用。
**解法**:在 lambda 顶部(任何 `if constexpr` 之前)预捕获:
```cpp
amrex::ignore_unused(变量A, 变量B, 变量C);
```
2026-08-07 的最新代码就撞了这个,补的是:
```cpp
amrex::ignore_unused(pressure_reconstruction_states,
                     pressure_reconstruction_component,
                     radial_domain_high_index);
```
另一种写法是把 `constexpr` 常量**声明在 lambda 内部**(而不是外层作用域)。

### 4.4 坑:`rm -rf tmp_build_dir` 不删旧 exe
make 失败后旧 `*.ex` 还在,会被当成"编译成功"跑起来,**得到上一版代码的结果**。
**永远 `rm -rf tmp_build_dir *CUDA.ex` 一起删,并在跑之前校验 exe 的时间戳。**

## 5. 怎么跑

**单卡一个算例**(2D 算例几乎都是这样):
```bash
cd <case_dir>
CUDA_VISIBLE_DEVICES=0 nohup mpirun -np 1 ./main2d.gnu.TPROF.MPI.CUDA.ex inputs \
    <参数覆盖...> > run.log 2>&1 &
```
**后台且不被 ssh 断开杀掉**(重要):
```bash
setsid nohup bash <你的脚本>.sh > /dev/null 2>&1 < /dev/null &
```

常用参数覆盖:
```
amr.restart=<chk目录>            # 断点续算
max_step=2000  stop_time=4.1e-3
amr.plot_int=200  amr.check_int=1000
amr.plot_file=./plot/plt  amr.check_file=./plot/chk
amr.max_level=4                  # 加密(重启时配 amr.regrid_on_restart=1)
cns.record_stats=1  cns.stats_start_time=1.5e-3   # 在线统计(注意:部分 2D 算例的
                                 # 统计状态描述符没注册,开了会 segfault,见 8.3)
```

**⛔ 绝对不要在 AWS 上提交 CPU 计算任务。** CPU 只允许秒级–分钟级的后处理(提取/渲染/拷贝/**编译**)。任何模拟腿必须在 GPU 上。

## 6. 并发:**每盒 2 条腿最划算**(实测,别猜)

同一算例、同一台盒的实测速率:

| 同时跑的腿数 | 每腿速率 |
|---|---|
| 1(独占) | **243 步/分** |
| 2 | ~120–240 步/分 |
| 8 | **16 步/分** |

**8 腿比独占慢 15 倍。** 主机 CPU(192 核,load 只有 10)和 NFS I/O(<1% 开销)都不是瓶颈——
是**每个进程狂发小内核**在 GPU 驱动/PCIe 层互相拖累。

**GPU 利用率参考**(2D 算例是 overhead-bound,不是算力受限):

| 算例规模 | GPU 利用率 |
|---|---|
| L3,~0.8M cells,8 腿并发 | 3–14% |
| L3,~0.8M cells,独占 | ~25% |
| **L4,D_e/256(真 m142)**,2 腿 | **34–63%** |

**结论**:
- **给一个 2D 算例加卡没用**(L0 只有 3 个盒,rank 超盒数还会 `Zmom=-nan` 秒崩);
- 想用满 8 卡 → 跑**多个不同算例**,但**每盒别超过 2–3 条**;
- 想提利用率 → **加网格**(L4/L5),不是加卡。

## 7. 监控(有个会骗人的坑)

⚠️ **不要在头节点上 `pgrep` 判断计算是否在跑**——计算进程在 **p5** 上,头节点看不到,
会误判"已结束"。**用 `/shared` 上日志文件的 mtime 判活**:

```bash
AGE=$(( $(date +%s) - $(stat -c %Y run.log) ))    # >300s 基本可判停止
grep -c "STATE CHECK FAILED" run.log              # >0 = 正性检查中止(崩了)
grep "Level 0 step" run.log | grep ADVANCE | tail -1   # 当前步/物理时间
```

常驻看门狗模板在 `/shared/npr20_retest/watchdog2.sh`(按 mtime 判活 + 崩溃写 `ALERT` 文件)。

## 9. 一个最小可用的完整流程

```bash
# 本地:找到新盒 IP
ssh aws-hpc 'cat /shared/npr10_ab/newbox.env'

# 本地:登 p5
ssh -J aws-hpc -i ~/.ssh/aws-hpc-us.pem ec2-user@<IP>

# p5 上:
sudo systemctl start nvidia-fabricmanager
sudo mount -t nfs -o nfsvers=4.1,_netdev 10.0.2.144:/shared /shared
source /shared/gpu_kit/gpu_env.sh
which nvcc && nvcc --version | tail -1        # 必须是 12.6

mkdir -p /shared/mycase && cd /shared/mycase
# 放 prob.h / inputs / GNUmakefile(AMR_SOLVER 指向选好的树)
rm -rf tmp_build_dir *CUDA.ex
make -j24 USE_MPI=TRUE USE_CUDA=TRUE CUDA_ARCH=90 DIM=2 > build.log 2>&1
ls *CUDA.ex || grep -i "error:" build.log | head

# 冒烟 2 步
CUDA_VISIBLE_DEVICES=0 mpirun -np 1 ./main2d*.ex inputs max_step=2 \
    amr.plot_int=-1 amr.check_int=-1 2>&1 | tail -5

# 生产(detached)
CUDA_VISIBLE_DEVICES=0 setsid nohup mpirun -np 1 ./main2d*.ex inputs \
    stop_time=4e-3 amr.plot_int=200 amr.check_int=1000 > run.log 2>&1 < /dev/null &
```

## 10. 安全边界(用户的硬规则,必须遵守)

1. **禁止在 AWS 上提交 CPU 计算任务**(只允许秒级–分钟级后处理/编译)。
2. **每一次起实例 / 提交作业,都要用户单独明确同意**。"能不能跑 X" 是咨询,不是授权。
3. **取消后重发 = 新提交**,同样要重新征得同意。
4. 唯一免问的动作是**纯止损的杀进程**(停止烧钱/防止数据损坏),杀完立刻汇报。
5. 接力链(A 完成自动跑 B)需要用户**预先明确授权**该次接力。
6. 已在跑的任务的衍生操作(监视/渲染/分析/提取)不受限制。
7. 时间戳一律用 **UTC**。
